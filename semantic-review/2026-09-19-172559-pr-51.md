# M9b spec review — archives and nested categories (PR #51, spec only)

Three documents specifying four new archive routes (nested category, tag, date, author), a `ParentID` on `domain.Term`, a descendant-aware published-post read, and one exported classifier in `internal/routing` that replaces chi registration order as the seat of route precedence. The spec is unusually well grounded: 15 of the 17 load-bearing factual claims about the existing codebase check out exactly, including line numbers for `term_taxonomy.parent` in all three vendors. The problems are concentrated in two places — one claim about an existing helper that is wrong in a way that will produce off-by-one-day archives, and a set of resolution/collision assumptions the spec never states, all of which are cheap to settle now and expensive to unwind after Phases 1–10 are built on them.

**Watch for:** `formatTS` converts to UTC, which contradicts Req 6.4's no-timezone-conversion promise and makes the cited `MediaFilter` precedent work only by accident (confirmed). Category and tag archive resolution silently depends on term slugs being unique within a taxonomy, resolved through a `LIMIT 1` with no `ORDER BY` — the exact nondeterminism the spec condemns in WordPress's own nicename read, and treated as a first-class problem there but unmentioned here (confirmed). Req 4.4's collision check misses a base colliding with the permalink structure's leading literal, which is WordPress's own Numeric preset and produces a 404 on every post URL (confirmed). The design's claim that a `Flat` structure "reduces to today's behavior byte for byte" is false and collides with Req 9.6 (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The spec's central structural bet — register every ambiguous pattern to one handler so chi's silent last-wins resolution at a parameter node becomes unobservable, then decide precedence in one pure classifier — holds up against the code it cites. `router.go`'s existing comment already records the collision behavior, and `resolveSingle` already derives components from `r.URL.Path` rather than chi's parameter names, so the classifier extends an established pattern. Keeping `routing.Parse`'s signature and adding two booleans avoids churning 25 call sites for no behavioral gain, and the "explicitly set to the default string" case that motivates the booleans is a real WordPress behavior that a naive default-comparison gets wrong.

The resolution path for a category archive is where the design is thinnest. It classifies a path into `Segments`, resolves the **final** segment to a term, then compares the term's real ancestry against the segments given. That makes the leaf slug the identity of the archive, and nothing in the schema or the spec makes a leaf slug unique within a taxonomy. The design already reads the entire taxonomy graph on every category request; resolving the whole segment path through that graph instead of through `TermRepo.BySlug` removes the assumption at no extra query cost and makes the wrong-ancestor comparison exact rather than inferred.

Date archives inherit a timezone hazard from the helper the spec names as precedent. `formatTS` calls `t.UTC()`, and `MediaFilter`'s bounds only survive that because the admin API parses them with `time.Parse`, which yields UTC. A `DateRef.Range` built in any other "fixed zone" shifts every boundary by that zone's offset. The half-open interval itself is correct across month, year and leap-year boundaries under `AddDate` semantics, and task 1.1 already tests the leap day; the zone is the whole risk.

Base-segment collisions are specified as a non-fatal `Notes()` diagnostic rather than a `Parse` error, which is the right channel. The check's coverage is too narrow: it compares the two bases against each other and against `author`, but not against the structure's own leading literal, and it does not normalize or reject a base value containing a slash. Both cases are representable in a database grimoire does not own, and both turn into total route failures rather than degraded ones.

The `ArchiveFilter` design (one filter type, `post_status='publish'` deliberately not a field, `EXISTS` instead of `DISTINCT`) is correct and portable across all three vendors. Its `Types` default of `{"post"}` matches WordPress for all four archive kinds, but it silently changes today's category archive, which applies no post-type predicate at all.

Making `render.CategoryData` a type alias is safe: every literal of it in the tree is keyed, so adding fields cannot break a caller at compile time or at template execution time.

## Claim verification

Fifteen of the seventeen claims are accurate as written. Reporting the two that are not, and the one that is imprecise, then the rest briefly.

**Wrong: `MediaFilter`'s `After`/`Before` are not a half-open range.** Req 6.4 and the design's `internal/storage/wprepo` section both cite them as the precedent for a half-open `[start, end)` comparison. `mediaWhere` does this:

```go
if !f.Before.IsZero() {
    // Before is the inclusive end of a calendar day (Requirement 5.3
    // treats after/before as ISO-8601 dates), so compare against the
    // start of the following day rather than excluding same-day rows.
    q = q.Where("p.post_date < ?", formatTS(f.Before.AddDate(0, 0, 1)))
}
```

`internal/storage/wprepo/media.go:78-83`. `Before` is an inclusive day-end, deliberately, with a comment saying so. The lower bound is inclusive as claimed. So the existing convention is `[After, Before+1day)`, not `[start, end)`.

That matters beyond the citation being loose, because `ArchiveFilter` declares fields with the **same names** in the **same package** and the opposite meaning:

```go
After    time.Time // inclusive lower bound on post_date; zero = unbounded
Before   time.Time // exclusive upper bound; zero = unbounded
```

Two filter types in `internal/domain` whose `Before` fields mean different things is a trap for whoever writes the third one. Either name the archive bounds differently (`Start`/`End`) or state the divergence from `MediaFilter` in the field comment.

**Wrong: `formatTS` converts to UTC.** Req 6.4 promises dates "compared in the post's stored local time with no timezone conversion," and names `formatTS` as the mechanism. `formatTS` is:

```go
func formatTS(t time.Time) string {
	if t.IsZero() {
		return "1970-01-01 00:00:00"
	}
	return t.UTC().Format(tsLayout)
}
```

`internal/storage/wprepo/helpers.go:23-28`. The `MediaFilter` path survives this only because the only producer of those bounds parses with `time.Parse("2006-01-02", raw)` (`internal/web/adminapi_media.go:95,103`), which yields UTC, making `t.UTC()` a no-op.

The design says `DateRef.Range` builds its interval "in a fixed zone" carrying "naive wall-clock time," and task 1.2 says "the same no-conversion basis `Canonical` already reads `post.Date` on." `Canonical` reads `p.Date`, which `parseTS` produced with `time.ParseInLocation(layout, s, time.UTC)` (`helpers.go:52`) — so that basis is UTC, and the task's phrasing points an implementer toward `time.Local` instead. On a UTC-7 host, a May 2024 archive would then query `2024-05-01 07:00:00` to `2024-06-01 07:00:00`: the first seven hours of May 1 missing, the last seven of April 30 included. Silent, plausible-looking, and reported months later.

The fix is one sentence in Req 6.4 and task 1.2: the interval is built in UTC so that `formatTS` is the identity, which is what "no conversion" actually requires given this helper.

**Imprecise: why `ByTermSlug` is currently correct.** The spec (design's semi-join section, task 3.4) says it "is correct only because it filters on a single `t.slug`, which can match at most one `term_taxonomy` row per post." The mechanism is really: `term_taxonomy` is unique on `(term_id, taxonomy)` (`sqlite/0001_init.up.sql:49`, `mysql:54`), so one `term_id` in one taxonomy has exactly one row. But `{prefix}terms.slug` carries a **non-unique** index (`sqlite/0001_init.up.sql:40`), so two `term_id`s can share a slug inside one taxonomy, and then the join multiplies exactly as the descendant case does. The claim holds under a within-taxonomy slug-uniqueness assumption that WordPress's write path provides and the schema does not — which is issue 1.

Everything else checks out as stated: `domain.Term`'s four fields (`entities.go:52-57`); `termRow` and all three term reads selecting exactly `t.term_id, t.name, t.slug, tt.taxonomy` with a `term_taxonomy` join already present (`repo.go:200-285`); `term_taxonomy.parent` at sqlite:48, mysql:51, postgres:48; `AdminPostFilter`/`MediaFilter`'s zero-value convention (`repository.go:62-76,151-159`); `content.Page`/`newPage`/`clamp`/`TotalPages`/`DefaultPerPage` (`content/pagination.go`) and `web.pageParam` (`handlers.go:26`); `PostService.WithCounter` as an opt-in dependency returning the receiver (`content/post.go:25`); `domain.TermReader.ListByTaxonomy` (`repository.go:323-331`); `restTerm.Parent` hard-coded `0` and `restTermLink`'s `"/category/"+slug` and `"/?tag="` (`rest_terms.go:76-98`); `userLink` and `commentLink` (`content/rest.go:214-221`); `category.tmpl`'s hard-coded `/category/{{.Term.Slug}}?page=` and `archive.tmpl`'s literal "Archive" heading with no pagination block; `CategoryPage`'s single production caller at `handlers.go:195` and `Category`'s zero; `Parse(structure, categoryBase, tagBase string)` collapsing an empty base with no record of which case occurred (`routing.go:111-116`, `351`); all of `ParamsFromPath`/`Match`/`Canonical`/`ChiPatterns`/`Flat`/`TrailingSlash`/`CategoryBase`/`TagBase`/`DefaultCategoryBase`/`DefaultTagBase`; `resolveSingle` deriving from `r.URL.Path` via `ParamsFromPath` (`handlers.go:96-98`); and `OptionService.Get` mapping absence to `""` (`content/option.go`). `routing.Parse` has 25 occurrences across `cmd/`, `internal/web`, `internal/content`, `internal/routing` and `test/e2e` (4 outside tests), so "twenty-odd" is accurate.

## Category archives are resolved by leaf slug

The design classifies `/category/news/local` into `Segments: ["news", "local"]`, resolves the last segment to a term, walks its real ancestry, and compares. The resolution read is:

```go
Where("tt.taxonomy = ?", taxonomy).
Where("t.slug = ?", slug).
Limit(1).
```

`internal/storage/wprepo/repo.go:216-219`. No `ORDER BY`. Two `category` terms slugged `local` — one under News, one under Sport — are schema-legal (non-unique slug index; `term_taxonomy` unique only on `(term_id, taxonomy)`), and the outcome is: whichever row the engine returns wins, the other category's archive is permanently unreachable, and a request for its correct canonical path `/category/sport/local` gets a `301` to `/category/news/local`. Across SQLite, MySQL and Postgres the winner can differ, which is precisely the objection the design raises against copying WordPress's unordered nicename read:

> grimoire runs on three vendors. Unordered row order diverges far more between SQLite, MySQL and Postgres than it ever does inside WordPress's MySQL-only world

The spec spends roughly a page on duplicate `user_nicename` — deterministic lowest-`ID` resolution, a cross-vendor contract case, a `migrate -check` report, a `docs/compatibility.md` divergence entry — and says nothing about the same condition on term slugs, even though the term case is on the resolution path of *every* category and tag archive request rather than only `/author/{nicename}`. An unstated assumption is worse than a documented divergence, and the asymmetry suggests it was not considered rather than judged acceptable.

The cheap fix is available and arguably better than the specified design: the handler already loads the whole taxonomy via `TermReader.ListByTaxonomy` to compute ancestry and descendants. Matching `Segments` **through that graph** — root slug among the taxonomy's roots, next segment among its children, and so on — resolves the archive by path rather than by leaf, removes the uniqueness dependency, and makes the wrong-ancestor `301` a direct consequence of the walk instead of a comparison after the fact. It also drops `TermRepo.BySlug` from the category path entirely. Retrofitting this after Phase 5 defines `CategoryArchive(ctx, segments, page, perPage)` in terms of leaf resolution, Phase 7 builds the `301` on the ancestry comparison, and Phase 8 reuses the graph for REST links means touching all three.

## The Numeric-preset collision

Req 4.4 checks `category_base` against `tag_base` and either against `author`. Now take WordPress's own Numeric preset, `/archives/%post_id%`, on a site whose `category_base` is `archives` — a rename an operator makes precisely because their URLs live under `/archives/`. Walk the design's precedence table:

- `CategoryBaseSet` is true (the option was provided), so row 2's expected prefix is empty.
- `/archives/123`: first segment equals `CategoryBase`, one further segment → `KindCategory`, `Segments: ["123"]`.
- `123` resolves to no category → `404`.

Every post on the site, 404, from its own canonical permalink. `Notes()` says nothing because the two bases don't collide with each other. chi says nothing because `/archives/{post_id}` and `/archives/*` are distinct patterns that both route to `s.resolve`. The design even names this structure — "WordPress's own 'Numeric' preset is `/archives/%post_id%`, whose literal front sidesteps the collision on its own" — while discussing the `date/` prefix, without noticing that the front it relies on is the same segment the base now occupies.

The front logic saves the unset-base case: with `category_base` unset, row 2's prefix *is* the front, so `/archives/123` fails row 2 (the segment after the prefix is `123`, not `category`) and falls through to row 7 as a post. The break happens only when a base is explicitly provided and equals a leading literal of the structure. Narrow, but it is the intersection of two things operators actually do.

This needs a row in the collision check (`Notes()` should name it) and a decision in the precedence table about which meaning wins. Given the milestone's premise — an existing site's published URLs keep working — the post interpretation probably should, with a loud note.

## Base values arrive unvalidated

`Parse` resolves a base like this:

```go
func firstNonEmpty(v, fallback string) string {
	if strings.TrimSpace(v) == "" {
		return fallback
	}
	return v
}
```

`internal/routing/routing.go:351`. Whitespace-only becomes the default; nothing else is touched. Until now that was inert, because no route consumed `CategoryBase`. M9b makes it the seat of chi pattern registration, path construction, `Classify`'s segment comparison and the REST `link` field.

Two representable values break all four. A base containing a slash (`topics/news` — WordPress's permalink settings page accepts a multi-segment base) makes `Classify`'s "first segment == `CategoryBase`" never true, so every category archive 404s while `CategoryPath` advertises `/topics/news/local`. A base with a leading slash makes `ArchivePatterns` emit `//topics/*`. The leading-slash case is worth checking against the live database rather than assuming: WordPress's `options-permalink.php` prefixes the submitted base with `/` before `update_option`, so `get_option('category_base')` plausibly returns `/topics` on any site where the base was set through the admin UI. The spec already quotes a live-database fact (`Non_unique = 1` for `user_nicename`), so one more query settles it.

The existing tests use `"sections"` (`cmd/grimoire/permalinks_test.go:162`), so nothing in the tree exercises either shape. Specify normalization in `Parse` (trim `/`, collapse repeats) and a `Notes()` entry for a base that normalizes to more than one segment, or state that multi-segment bases are unsupported. Doing it in Phase 1 is a few lines; doing it after Phase 7 means revisiting `Classify`, `ArchivePatterns` and all four constructors.

## Flat structures do not reduce to today's behavior

The design's precedence-table section closes with:

> When the structure is `Flat` there is no front (a flat `Structure` has no segments at all), so every prefix is empty and the table reduces to today's behavior byte for byte.

Rows 2–5 do. Row 6 does not. With every prefix empty, a single 4-digit numeric segment matches row 6 and classifies as `KindDate`, ahead of row 8's flat-slug reading. Today `/2024` on a plain-permalink site reaches `/{slug}` (`router.go:196`) and resolves a post slugged `2024` — the slug WordPress generates for a post titled "2024". After M9b it is a year archive, and the post is unreachable.

Req 9.6 lists "the flat `/{slug}` fallback" among the routes whose behavior must not change, and task 7.4 asserts that by test. So the requirement and the precedence table contradict each other; which one a reviewer believes decides whether task 7.4 passes.

Worth noting what WordPress does here, since the milestone's posture is compatibility: with plain permalinks WordPress registers no rewrite rules at all, and date archives are `/?m=2024`, not `/2024`. grimoire already diverges by serving `/category/{slug}` under plain permalinks, so extending the divergence to date archives is defensible — but it is a choice, and it has a cost that the spec currently claims does not exist. Either gate date archives on a non-`Flat` structure, or document the flat case alongside the `/%postname%/` consequence already listed and narrow Req 9.6.

## `Types` defaulting to `{"post"}` changes an existing archive

Req 3.5 says the archive lists `post_type='post'` rows only, "matching `PostRepository.RecentPosts` and WordPress's own archive queries." `RecentPosts` does filter (`repo.go:93`). The current category archive does not: `ByTermSlug` (`repo.go:168-189`) and `CountPublishedByTermSlug` (`repo.go:230-240`) filter on taxonomy, slug and `post_status='publish'`, with no post-type predicate at all. A published `page` assigned to a category appears in the category archive today and will stop appearing.

`{"post"}` is the right default for all four kinds against WordPress. But this is a user-visible removal on an existing route, and task 10.6's compatibility-doc list — which does cover the precedence consequences, the `?page=` divergence and the nicename divergence — does not mention it. Task 3.1 hints at awareness ("`Types` defaulting to `{"post"}` so pages do not leak into archives") without connecting it to current behavior.

## `TermsByIDs` cannot honor Req 1.2

Req 1.2: "A term read through one path and the same term read through another SHALL NOT disagree about its parent." The three reads are not equivalent, though. `BySlug` and `ListByTaxonomy` filter `tt.taxonomy`; `TermsByIDs` does not:

```go
Join("JOIN ? AS tt ON tt.term_id = t.term_id", bun.Ident(r.prefix+"term_taxonomy")).
Where("t.term_id IN (?)", bun.In(ids)).
```

`internal/storage/wprepo/repo.go:270-272`. Since `term_taxonomy` is unique on `(term_id, taxonomy)` rather than on `term_id`, a `term_id` registered in both `category` and `post_tag` returns two rows with different `taxonomy` **and** different `parent`. `ParentID` is a property of the `(term_id, taxonomy)` pair, and `TermsByIDs`'s signature cannot express which one the caller wants. WordPress 4.4's term splitting makes shared term IDs rare in practice, but "rare" is what the rest of this spec refuses to rely on. Either narrow the requirement to the taxonomy-scoped reads, or give `TermsByIDs` a deterministic rule.

## Fixture churn is underestimated

Task 2.1 extends `storagetest.SeedFixtures` with "a nested category chain — parent, child, grandchild, each with a post." `SeedFixtures` is shared well beyond the contract suite: `internal/web/handlers_test.go:49`, `auth_test.go:77`, `rest_terms_test.go:62`, `rest_router_test.go:56`, `rest_apppassword_comments_test.go:51`.

Three new published posts collide with assertions that are absolute, not relative:

```go
if len(posts) != 3 {
    t.Fatalf("want 3 posts, got %d", len(posts))
}
wantSlugs := []string{"hello-3", "hello-2", "hello-1"}
```

`internal/storage/storagetest/contract.go:224-228`. Also `contract.go:573` (a count of 3), `web/rest_terms_test.go:115` ("SeedFixtures seeds 3 category terms"), and `web/permalinks_test.go:17`, which documents the fixture post set its expectations derive from. Home-page pagination tests inherit the same total.

The nested chain has to exist somewhere, but it does not have to be in the shared fixture with new posts. Either add a separate `SeedNestedTerms` used only by the new cases, or attach the nested terms to posts that already exist so no count changes. Otherwise Phase 2 quietly becomes a cross-package test-update phase.

## Interface placement and reporting branches

`DuplicateNicenames` is specified on `domain.UserRepository`. That type is held by `auth.Sessions`, `auth.ApplicationPasswords`, `content.UserService` and `web.Server.restUsers` — every request path — for the sake of a method reachable only from `grimoire-cli migrate -check`. It also forces the two existing fakes (`internal/auth/session_test.go:30`, `internal/content/userservice_test.go:22`) to grow a method they never call. The codebase's own pattern is the opposite: `TermReader`, `PostCounter` and `MediaWriter` are narrow interfaces added beside the big ones rather than into them. A `NicenameAuditor` consumed only by grimoire-cli costs nothing and keeps the audit off the request-path type. `ByNicename` on `UserRepository` is correct — it has a request-path caller.

Both reporting call sites return early before the point where bases would be printed. `reportPermalinks` returns in the unsupported branch and again in the `Flat` branch; `resolvePermalinks` logs no bases at all in the unsupported branch (`cmd/grimoire/permalinks.go:31-48`), and does log them when `Flat`. The resolved bases and any `Notes()` entries are meaningful in all three branches — a plain-permalink site with `category_base` set still serves its archives at that base, because `Parse` populates the bases before the flat early return — so a naive "append the bases at the end" implementation would report nothing for the two most common configurations. Tasks 9.2 and 9.3 should say "in every branch."

## Smaller precision items

The `date/` disambiguation rule is keyed on WordPress's token index, and WordPress's `get_date_permastruct()` counts only `%...%` matches, not path segments. So `/archives/%year%/%monthnum%/%post_id%/` fires the prefix (post_id is token 3) while a segment-counting implementation puts it at 4 and does not. Task 1.6's table covers positions 1–4 but only with structures that have no literals, so it cannot catch that mistake. Add one literal-carrying case.

Req 10.2 promises that an advertised REST link "is a URL that returns `200` rather than one that `301`s or `404`s." In the Req 4.4 collision case the colliding segment keeps the category meaning, so `TagPath`'s output classifies as a category and the tag's `link` does not return `200`. State the exception rather than letting two requirements contradict.

`CategoryBaseSet` is defined as "the corresponding option arrived non-empty" while `firstNonEmpty` treats whitespace-only as empty. A base of `" "` would then resolve to `category` **and** count as provided, dropping the front for a base that was effectively unset. One emptiness test, used in both places.

The design's SQL sketch writes `tr.object_id = p.ID` and `ORDER BY p.post_date DESC, p.ID DESC`. Postgres declares the column as `"ID"` (`postgres/0001_init.up.sql:6`), where unquoted `p.ID` folds to `p.id` and errors; every existing read uses `bun.Ident("ID")`, and `helpers.go`'s `execQuerier` comment documents the family of traps this belongs to. Illustrative SQL, but worth getting right in a document implementers will copy from.

`user_nicename` has no index in any of grimoire's migrations (the column is declared at sqlite:65, mysql:69, postgres:65; the only `users` index is on `user_login`). `/author/{nicename}` is therefore a full table scan per request on a grimoire-created database. WordPress-created databases carry WordPress's index, so the reference site is fine. Adding one would break the zero-migration property the milestone leans on, so the right move is probably a sentence acknowledging it.

`ByTermSlug` and `CountPublishedByTermSlug` lose their last production callers when task 5.7 removes `Category` and `CategoryPage` — `internal/content/term.go:32,49,53` are the only ones. Task 3.4 keeps them "untouched" on the grounds that they are "the single-slug, non-descendant read," which is a role with no consumer. They stay on `domain.PostRepository` and `domain.TermRepository` (`repository.go:32,42`), so every implementation and fake keeps carrying them.
